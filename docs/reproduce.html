Reproduce the Results

You can re-run every number on this site from the backup-node-selection package. Trained RL models are included, so you do not need to train anything.

Linux (tested on Ubuntu / WSL2) Python 3.10 ~2 GB disk (mostly PyTorch) No root · no Mininet · no SDN controller

1Get the code and set up

git clone https://github.com/bijoy111/ideft.git
cd iDEFT/backup-node-selection/code

python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

All commands on this page run from inside backup-node-selection/code/. You can also grab the package from the Downloads page.

2Quick check that it works

python3 backup_selector.py --mode heuristic --seed 42 --out /tmp/mapping.json
python3 rpc_contention_experiment.py --context-seeds 42 --trials 1 --calls 50 --burst 4 \
    --methods baseline heuristic

You should see the mapping each method picked, then a summary table of latency numbers and a Mann-Whitney comparison. If that runs, your setup is ready. Everything below uses the same code with bigger settings.

⚠ One mistake will quietly spoil your results: the scripts add to results_rpc/*.csv instead of replacing it, and the summary at the end reads the whole file. Delete the CSV before each scenario. Every block below starts with rm for this reason. If you skip it, results from different runs get mixed together.

6Heuristic weight sensitivity & decay calibration → paper §V-G, Table VIII

This answers a natural question about the multi-criteria heuristic: are its scoring weights (0.35, 0.35, 0.20, 0.10) and its load-decay mechanics (cap -= 20; health *= 0.95) principled, or ad hoc? The sweep scores all 287 weight configurations (a 0.1-step grid over the 4-simplex, plus the published default) across the 9/16/32/128-host topologies, 5 seeds each — measuring degraded-host hits, maximum per-backup load, and distinct backups used. It calls the real select_backups directly, so it needs no RPC servers and runs in seconds. 

python3 weight_sensitivity.py

Result (5-seed average): degraded-host avoidance is weight-independent — all 287 configurations avoid degraded hosts at every scale (including weighting 100% on hop-count alone). Load-balancing is driven almost entirely by the capacity term (its -20 decrement is the load-spreading mechanism); latency/hops carry no weight in these uniform-hop topologies. The published default lands within one unit of the best possible max-load and uses 90–94% of the maximum distinct backups — a principled, near-optimal choice, not an arbitrary one. Full run saved in findings/weight_sensitivity.txt.

7Hash baselines, a fairer round-robin & topology diversity → paper §V-H, Table IX

Compares decentralized hash placements — the NFV analog of CRUSH/Dynamo — and a fairer round-robin against the feature-aware methods, structurally (degraded-host hits + max per-backup load, no RPC), over both single-hub star and multi-hub topologies. hrw is plain (quality-unaware); weighted_hrw and weighted_chash (Dynamo-style consistent hashing) weight by health×capacity; rr_random is round-robin with a random offset.

8Cross-algorithm check: DQN vs PPO → paper §V-F, Table VII

Is the load-balancing gap a PPO quirk, or a property of the problem? DQN answers that: it runs through the same environment, reward, and inference path as PPO, with only the learner swapped (off-policy replay + epsilon-greedy instead of on-policy actor-critic + entropy bonus). Both are scored structurally — distinct backups used, peak per-backup load, degraded-host assignments. Those are properties of the mapping rather than of RPC timing, so unlike latency they are hardware-independent and reproduce exactly on any machine. This needs no RPC servers and runs in about a minute:

Result: up to 32 hosts the two algorithms behave alike — but DQN only gets there after the same class of fix PPO needed at 128 hosts (with library defaults it collapsed to 2–4 backups of 20; widening exploration to fraction 0.7, final eps 0.15, buffer 100k, 150k steps recovered it). At 128 hosts DQN collapses to 1–3 distinct backups of 80, piling up to 80 primaries on one host, and puts 172/400 assignments on degraded hosts. Since two architecturally different RL algorithms concentrate the same way and respond to the same remedy, the gap points at the problem formulation rather than at one algorithm. Full run in findings/rl_algorithm_comparison.txt.

You can also drive DQN through the full RPC harness with the rl_dqn method, or check a single checkpoint's spread directly: 

# DQN inside the RPC latency harness, alongside PPO
rm -f results_rpc/rpc_contention_raw.csv

    --methods heuristic optimal rl rl_dqn \
    --n-hosts 32 --n-primaries 20 --n-degraded 4 --scale-seed 0 \
    --rl-model rl_model_scaled32.zip --rl-dqn-model rl_model_dqn_scaled32_mitigated.zip

# Single-checkpoint collapse check (seconds)

# See the collapse for yourself: PPO's default settings break down at 128 hosts
python3 rl_backup_selector.py --train --check-collapse --timesteps 400000 \

python3 rl_backup_selector.py --train --check-collapse --timesteps 1000000 \
    --model rl_model_scaled128_v3.zip \
    --n-hosts 128 --n-primaries 80 --n-degraded 16 --scale-seed 0 \

# --- DQN (add --algorithm dqn; DQN uses exploration flags instead of --ent-coef) ---
python3 rl_backup_selector.py --train --algorithm dqn --timesteps 50000 --model rl_model_dqn.zip
python3 rl_backup_selector.py --train --algorithm dqn --timesteps 80000 \
    --model rl_model_dqn_scaled.zip \
    --n-hosts 16 --n-primaries 10 --n-degraded 2 --scale-seed 0

# 32 hosts: DQN collapses on defaults, so this is the mitigated config (16-19 of 20 backups)
python3 rl_backup_selector.py --train --algorithm dqn --check-collapse --timesteps 150000 \
    --model rl_model_dqn_scaled32_mitigated.zip \
    --n-hosts 32 --n-primaries 20 --n-degraded 4 --scale-seed 0 \
    --exploration-fraction 0.7 --exploration-final-eps 0.15 \
    --buffer-size 100000 --target-update-interval 1000

# 128 hosts: still collapses (3 of 80 backups) even with a wide network and long training
python3 rl_backup_selector.py --train --algorithm dqn --check-collapse --timesteps 1000000 \
    --model rl_model_dqn_scaled128.zip \
    --n-hosts 128 --n-primaries 80 --n-degraded 16 --scale-seed 0 \
    --net-arch 256 256 --batch-size 256 --buffer-size 100000 --exploration-fraction 0.5
Tip: always add --check-collapse when you train at a new size. It prints how many different backups the policy uses across 5 seeds, so you catch a bad policy straight away instead of part-way through a full run.

Common problems

  • Running the commands from a script: a cd in one shell command does not carry over to the next one. Use cd path && command on each line, or full paths.
  • SimpleXMLRPCServer only queues 5 waiting connections by default. When many primaries share one backup (concentrated, 80 on one), hitting that limit is part of the result. Do not raise the limit to "fix" it, or you are no longer measuring what DEFT actually ships. The retry-with-backoff in the harness handles it and records the failures as data.
  • The RL policy can collapse at any new size, not just 128 hosts. That is why --check-collapse is there.
  • NameError: name 'json' is not defined means the one-line config.py import fix is missing. It is already applied in this package.
