Bare Metal: the 128-Host Measurement, Done Properly

The 128-host page withdrew its latency numbers because one machine cannot host 128 backup servers and the client measuring them. This is that measurement repeated on ten bare-metal nodes, each backup pinned to its own physical core, with degraded hosts slowed by the Linux kernel rather than by a sleep inside the server. It confirms the central finding — and revises two magnitudes sharply downward.

CloudLab Utah, 11 × c6525-25g 16-core EPYC 7302P, 25 GbE 128 backups, 1 physical core each 5 seeds × 3 trials (15 runs) degradation by tc netem
The setup. Ten nodes carry the 128 backup servers, thirteen per node except the last; an eleventh node runs the client alone. Each server is launched under taskset on a core of its own. Hyperthread siblings on this processor pair as (0,16), (1,17), … so logical CPUs 2–14 are fourteen distinct physical cores — no two servers share one core's two threads. The claim that each backup owned a core is checked, not asserted: provisioning writes the intended core into a manifest, and a verification pass reports the affinity each server actually holds. All replication traffic crosses the 25 GbE experiment LAN.

Result 1: with identical hosts, selection does not matter

When every candidate backup is equivalent, a selector that reads node features has nothing to read. All four sensible methods land within half a millisecond of each other.

What this means: the feature-aware methods route around degraded hosts completely, while the ordering-based ones meet them at the base rate of 12.5%, and the latency follows — p99 roughly halves. Every one of these comparisons has r = −1.000 over 15 paired runs, meaning not one run dissents. And heuristic vs optimal is not significant on either mean or p99: the cheap greedy scorer attains the quality of the capacity-constrained Hungarian assignment without solving one.

Result 3: DEFT's accept queue, tested directly

DEFT builds its backup from Python's SimpleXMLRPCServer with no arguments, so its TCP listen backlog is the library default of five, while XML-RPC opens a fresh connection for every call. The paper already identified this as the cause of the latency tail. The testbed lets us test it directly: hold everything else fixed and change only that integer.

Methodp95 @ backlog 5p99 @ backlog 5p95 @ backlog 512p99 @ backlog 512
optimal64.941040.0665.7178.81
heuristic66.791042.4765.5480.57
round_robin66.671039.9666.0580.09
random65.491051.6765.4779.24
Four methods whose p95 differs by under 2 ms have p99 values within 12 ms of 1040 ms. A constant that survives every change of method is an artifact, and one second is Linux's initial TCP retransmission timeout. The kernel counters confirm it: 103,209 ListenOverflows on the most heavily selected node against just 116 retransmitted segments, with ListenDrops equal to ListenOverflows exactly. The connections were refused at the server, not lost in the network. Raising the backlog to 512 took the overflow count to zero.

Why this matters for the placement result

The backlog does not just move the tail. It changes how expensive sharing a backup appears to be:

7.5× becomes 35%. Under the shipped backlog, piling 79 primaries onto one backup looks catastrophic. With a properly sized accept queue the same sweep costs about a third more. Most of the apparent penalty for concentration was connection setup being refused, not queueing at the backup. The effect is real, but considerably smaller than the shipped configuration suggests.

The backlog's bias does not have a single sign

Two surprises here, and one of them corrects us.

First, the one-second plateau appears at 16 hosts too (1013–1023 ms), on hardware where nothing else is contended. It was never specific to 128 hosts — it has been bounding p99 at every scale in this work.

Second, the gap between methods is larger once the backlog is fixed: round-robin minus heuristic is 3.18 ms as shipped and 6.07 ms at backlog 512. At 128 hosts the shipped queue inflated the concentration penalty; at 16 hosts it understates the placement gap. Overflow tracks concentration, and with 10 primaries over 16 backups nothing is concentrated enough for it to fall selectively on the bad placements. So the backlog biases a measurement, with a sign that depends on the workload — which is a better reason to treat it as a controlled variable than if it simply scaled everything.

Third, the five-deep queue lowers the median (22.68 → 14.64 ms). A short accept queue is admission control: accepted calls contend with fewer others and finish faster, refused ones wait a full second. DEFT as shipped trades a better median for a catastrophic tail.

How degradation was imposed

The deployment refuses to simulate a degraded backup by sleeping inside a server it did not start — a sleep is exactly as long as we said it would be, costs no CPU and queues nothing. So the heterogeneous arm slows hosts physically with tc netem.

tc attaches to an interface, but each node here carries thirteen backups, and shaping the interface would degrade their healthy co-tenants — the very hosts the comparison needs as controls. Each backup owns a distinct TCP port, so a prio qdisc with a u32 filter on source port delays exactly the degraded servers. The fourth band of a four-band prio is unreachable through the default priomap, so healthy flows never enter the netem queue at all rather than being delayed by zero.

Adjacent ports on the same NIC, two orders of magnitude apart. The 101 ms is itself informative: netem delays every packet the server sends, so a connection-per-call protocol pays the added latency twice — once on the SYN-ACK and once on the response.

A caution worth publishing. An earlier execution degraded the first sixteen backup-eligible hosts, a contiguous block, and reported round_robin tied with optimal at 41.3 ms having touched a degraded host 0% of the time. That tie was an artifact of naming. round_robin cycles a lexicographically sorted host list, in which every name beginning w1–w7 precedes w8; with 80 primaries the cursor advances 80 positions and never reaches the block. It scored zero by never arriving, not by avoiding. Spreading the same sixteen degraded hosts evenly along that ordering puts them inside every method's reach, after which round-robin meets them at the base rate and its mean rises from 41.28 to 51.87 ms. A load-spreading baseline evaluated against a contiguous impairment can appear to avoid it.
Two things this page does not claim. First, concentrated's 260 ms in the degraded arm mixes concentration with degradation, because the host it piles onto is itself degraded; the clean figure for concentration alone is the homogeneous column, 56.27 against 41.73. Second, the 16- and 32-host scenarios have since been re-run here, and the result holds at both; the 9-host page remains a single-machine measurement. The "upper bound" caution that used to sit here was also wrong in direction at small scale — see the backlog comparison above.
