\begin{abstract}
Network Function Virtualization (NFV) systems that provide fault tolerance through
state replication (OpenNF, Pico Replication, FTMB, REINFORCE, and DEFT among them)
all replicate a primary network function's (NF) state to a backup instance, yet none of
them specify \emph{how that backup instance is chosen}. In DEFT, for example, the
Failure Detection Unit simply ``assigns'' a new secondary NF with no stated criterion.
This paper closes that gap with iDEFT (intelligent DEFT), which designs and evaluates
three backup-selection strategies as
drop-in replacements for DEFT's static, hand-assigned mapping: a multi-criteria greedy
heuristic (health, remaining capacity, network latency, hop-count), a globally optimal
assignment under per-backup capacity constraints solved exactly via the Hungarian
algorithm, and a Proximal Policy Optimization (PPO) reinforcement-learning policy trained
on the same objective with invalid-action masking. We evaluate all three, together with
naive baselines (DEFT's shipped static mapping, uniform-random, round-robin, and a
worst-case concentrated assignment), by driving DEFT's real, unmodified two-phase-commit
(2PC) backup implementation under controlled concurrent load, across four topology scales
(9, 16, 32, and 128 hosts) with rigorous multi-seed statistical testing (Mann-Whitney $U$
tests, rank-biserial effect sizes, bootstrap confidence intervals). We find that
feature-aware methods reliably avoid degraded backup hosts and substantially reduce tail
latency compared to blind load-balancing once hosts differ in quality, that a well-designed
deterministic heuristic tracks the Hungarian-optimal bound closely at every scale tested,
and that the learned RL policy matches this performance up to 32 hosts but requires
non-default hyperparameters to avoid a degenerate policy collapse at 128 hosts; even
after that fix, it still under-performs the heuristic on load-balancing precision at that
scale. We report this honestly as a precisely characterized limitation rather than a
solved problem: RL learns host-quality discrimination faster than it learns
load-balancing precision as the action space grows. The code, trained models, and the
saved output of every experiment are available for reproduction at
\url{https://bijoy111.github.io/ideft/}.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Network Function Virtualization (NFV) replaces dedicated hardware middleboxes with
virtualized network functions (NFs) running on commodity servers, enabling elastic
scaling and fault tolerance that fixed hardware cannot provide~\cite{han2015network}.
A stateful NF's correctness depends on preserving per-flow and global state across
failures and load-driven scaling events. The dominant approach to fault tolerance for
stateful NFs is \emph{replication}: a primary NF instance forwards its state updates to
one or more backup (secondary) instances, which take over processing if the primary
fails~\cite{rajagopalan2013pico,sherry2015rollback,kulkarni2018reinforce}. DEFT~\cite{shahriyar2023deft}
extends this line of work with a distributed, controller-free two-phase-commit (2PC)
protocol that achieves both elastic scaling and fault tolerance with strong consistency
on global state updates, without the single point of failure a central controller
introduces.

\subsection{The Gap: Backup Selection Is Never Specified}

Across this entire line of work, backup assignment is treated as solved by fiat rather
than as a decision with consequences. DEFT's Failure Detection Unit ``assigns NF B as
the new primary and NF C as the new secondary NF''~\cite{shahriyar2023deft} with no
stated criterion for choosing C. REINFORCE~\cite{kulkarni2018reinforce} designates
``a predecessor node and a backup node'' per NF without describing a selection rule.
OpenNF~\cite{gember2014opennf}, Split/Merge~\cite{rajagopalan2013split},
StatelessNF~\cite{kablan2017stateless}, and S6~\cite{woo2018elastic} all describe
\emph{how} state is migrated or shared once a target instance is known, never how that
target is chosen in the first place. In DEFT's own reference implementation, this
manifests concretely: the shipped static mapping for its 9-host evaluation topology
concentrates 3 of 5 primaries onto a single backup host, with no load or health
awareness whatsoever.

This is a consequential gap. The entire point of replication for fault tolerance is
that the backup must be available and capable of taking over. If the backup itself is
overloaded, unhealthy, or already serving many other primaries, the replication
mechanism's guarantees are only as good as an arbitrary assignment allows. Elastic
scaling compounds this: as NF instances are added and removed under varying load, a
backup pool's composition changes continuously, and a static or naively-assigned mapping
cannot track it. We deliberately scope this work to the fault-tolerance half of state
management, namely replication, because that is where the backup-selection decision lives.
Choosing a target for state \emph{migration} during elastic scaling is a related but
distinct decision, and our assignment formulation could extend to it, but we do not
evaluate it here.

\subsection{Contributions}

We present iDEFT (\emph{intelligent DEFT}), addressing backup-node selection directly
and using DEFT as the concrete system under study (though the problem and our methods
generalize to any primary/backup replication scheme). Specifically, we:

\begin{enumerate}
\item Formulate backup selection as a feasibility- and load-aware assignment problem,
and design three solutions spanning a deterministic multi-criteria greedy heuristic, an
exact globally-optimal assignment (Hungarian algorithm) under capacity constraints, and
a learned PPO policy with invalid-action masking during training.
\item Build a reproducible evaluation harness that drives DEFT's real, unmodified 2PC
backup implementation under controlled concurrent load via XML-RPC, isolating the
backup-selection mechanism from confounding Mininet~\cite{mininet}/SDN-controller environment issues
(\S\ref{sec:methodology}).
\item Evaluate all methods against DEFT's shipped static mapping and three naive
baselines (random, round-robin, worst-case concentrated) across four topology scales (9
to 128 hosts), with rigorous multi-seed statistical testing rather than single
point-estimate comparisons.
\item Measure not only tail latency but also RPC throughput, failure rate, and
per-mapping selection-time overhead, to directly support the elastic-scaling claim that
selection itself must be fast.
\item Report an honest, mechanistically-characterized limitation of the RL approach at
128-host scale, together with the two escalating hyperparameter fixes attempted, rather
than suppressing a negative result.
\end{enumerate}

The remainder of this paper is organized as follows. \S\ref{sec:related} surveys elastic
and fault-tolerant NF state management and RL-based NFV resource management, and states
our positioning precisely. \S\ref{sec:methods} describes the backup-selection methods.
\S\ref{sec:methodology} describes the experimental testbed and statistical methodology.
\S\ref{sec:results} presents results. \S\ref{sec:threats} discusses threats to validity.
\S\ref{sec:conclusion} concludes.

\section{Related Work}
\label{sec:related}

\subsection{Elastic State Management}

State management during NF scaling events follows two strategies: state migration and
migration avoidance.

\textbf{State migration.} Split/Merge~\cite{rajagopalan2013split} introduces partitioned
(per-flow) and coherent (global) NF state; coherent updates are periodically merged and
so remain eventually consistent~\cite{vogels2008eventually,burckhardt2014principles,bailis2013eventual}
across replicas, though in-flight traffic arriving at the source NF during migration is
dropped. OpenNF~\cite{gember2014opennf} uses \emph{move}, \emph{copy}, and \emph{share}
operations to achieve varying consistency levels in NF state sharing, with \emph{share}
achieving strong~\cite{vukolic2016eventually} or strict~\cite{adve1996shared,mosberger1993memory}
consistency; both systems require a central controller to coordinate migration.

\textbf{Migration avoidance.} StatelessNF~\cite{kablan2017stateless} and
S6~\cite{woo2018elastic} avoid migration by decoupling state from processing to varying
degrees. StatelessNF~\cite{szalay2019industrial} makes states globally accessible via a
remote data store, adding per-packet latency and introducing a single point of failure.
S6 stores states in a distributed shared-object space addressed via a Chord-like
key/object layer~\cite{stoica2003chord}, minimizing (but not eliminating) migration
through method-call shipping, local caching, and object replication with eventual
consistency.

\subsection{Fault-Tolerant State Management}

Pico Replication~\cite{rajagopalan2013pico} uses frequent checkpointing~\cite{plank1994libckpt}
for loss-free failure recovery, at the cost of not handling in-flight packets that arrive
during checkpointing. FTMB~\cite{sherry2015rollback} instead uses infrequent
checkpointing with packet-level logging and replay, favoring high steady-state throughput
over checkpoint frequency. REINFORCE~\cite{kulkarni2018reinforce} combines both
strategies: packets are buffered at a predecessor node and replayed to a backup node on
failure, with lazy checkpointing (transmitting only a timestamp table per batch) except
when a batch contains non-deterministic packets~\cite{cachin2016non}, which force strict
checkpointing. All three systems assume a backup already exists for each primary and
describe only the replication/recovery protocol; none describe how that backup is
chosen. DEFT~\cite{shahriyar2023deft} unifies elastic scaling and fault tolerance in one
system via a distributed 2PC protocol with no central controller dependency
(unlike~\cite{gember2014opennf,rajagopalan2013split,dixit2013towards}), but inherits the
same gap: backup assignment is a bookkeeping step in its Failure Detection Unit, not a
studied decision.

\subsection{Reinforcement Learning for NFV Resource Management}

A separate line of work applies reinforcement learning to NFV resource-management
decisions, almost entirely focused on \emph{primary} placement, scaling, or embedding
rather than backup/replica selection. Cand-RL~\cite{santos2022reinforcement} uses PPO to
optimize availability-aware Service Function Chain (SFC) placement.
DDQN-VNFPA~\cite{pei2019optimal} uses Double Deep Q-Networks for VNF placement in
SDN/NFV-enabled networks, reducing rejection rates. He et al.~\cite{he2023leveraging}
jointly optimize VNF placement and routing with an attention-augmented DRL agent.
MAPLE~\cite{wahab2019maple} proactively adjusts VNF placement via clustering and integer
linear programming. AREL3P~\cite{bunyakitanon2020end} uses end-to-end performance
prediction with RL for autonomous placement in 5G networks. DeepOpt~\cite{sun2020combining}
combines DRL with graph neural networks for topology-generalizing VNF placement, and Lun
et al.~\cite{lun2021virtual} address large state spaces and slow convergence in SFC
placement optimization. Kibalya et al.~\cite{kibalya2021reinforcement} apply RL to the
placement of \emph{stateful} VNFs specifically, but the state under consideration is the
primary's own execution state, not a fault-tolerance replica relationship between two NF
instances. The nearest neighbor to our work is Avgeris et al.~\cite{avgeris2023reinforcement},
an RL-based self-healing agent that \emph{repositions} VNFs after a failure or
resource-contention event has already been detected: a reactive decision, made after
the fact, rather than the proactive backup-assignment decision this paper studies as
part of setting up replication itself. Two recent surveys, Lim et al.~\cite{lim2023reinforcement}
on RL for virtual network embedding and Saha et al.~\cite{saha2023deep} on RL for network
slice scaling and placement, both catalogue placement, scaling, and embedding as the
RL-addressed sub-problems of NFV resource management; backup/replica selection for fault
tolerance appears in neither, underscoring that it is an open sub-problem rather than a
solved one being re-attempted here.

\subsection{Positioning of This Work}

Outside NFV, the principle that \emph{replica placement itself deserves algorithmic
attention} is well established in distributed storage systems: CRUSH~\cite{weil2006crush}
computes failure-domain- and load-aware placement of replicated data without a
centralized lookup table, and Dynamo~\cite{decandia2007dynamo} uses consistent hashing
with preference lists to spread replicas while accounting for heterogeneous node
capacity. Both treat ``which node holds the copy'' as a first-class, criteria-driven
decision: precisely the decision DEFT and its predecessors leave unaddressed for backup
NF assignment. This paper closes that gap for stateful NFV fault tolerance, building
directly on DEFT's 2PC replication mechanism, and evaluates the closure with a level of
statistical rigor (multi-seed testing, effect sizes, bootstrap confidence intervals) not
present in DEFT's own original evaluation or in the RL-for-NFV placement literature
surveyed above, which typically reports point-estimate comparisons against a single
baseline run.

\section{Backup-Selection Methods}
\label{sec:methods}

Let $P$ be the set of primary NFs and $H$ the set of all hosts (a superset of $P$; any
host not currently a primary for a given flow, and not an infrastructure host such as the
client or stamper, is a feasible backup for that primary, including hosts that are
primaries for other flows). For each primary $p \in P$ we must choose a backup
$b \in H \setminus \{p\}$. Each candidate host $h$ has a dynamic resource state: health
$\mathrm{health}(h) \in [0,1]$, remaining capacity $\mathrm{cap}(h)$ out of
$\mathrm{cap}_{\max}(h)$, CPU/storage availability, and a topology-derived hop-count and
latency to $p$.

\subsection{Baselines}

\textbf{Static (DEFT's shipped mapping).} The hand-assigned mapping DEFT ships with for
its 9-host reference topology, regenerable on demand for direct comparison.

\textbf{Concentrated.} Every primary assigned to the same single feasible backup: a
scale-independent, maximally naive worst case, generalizing DEFT's own static mapping's
tendency to over-concentrate load onto one host.

\textbf{Random.} A uniformly random feasible backup per primary, seeded for
reproducibility: a sanity floor any non-random method should beat.

\textbf{Round-robin.} Cycles through the sorted list of all feasible hosts, skipping a
candidate only when it equals the primary itself. Load-balances blindly, with zero
awareness of host health, capacity, or latency.

\subsection{Heuristic: Multi-Criteria Greedy Scoring}

For each primary (processed in a fixed order), the heuristic scores every feasible
candidate $c$ as
\begin{equation}
\begin{split}
\mathrm{score}(p, c) ={}& w_h \cdot \mathrm{health}(c) + w_k \cdot \frac{\mathrm{cap}(c)}{\mathrm{cap}_{\max}(c)} \\
&- w_\ell \cdot \hat\ell(p,c) - w_d \cdot \hat{d}(p,c)
\end{split}
\end{equation}
where $\hat\ell$ and $\hat{d}$ are the min-max-normalized latency and hop-count from $p$
to $c$ among $p$'s candidates, and default weights
$(w_h, w_k, w_\ell, w_d) = (0.35, 0.35, 0.20, 0.10)$ favor health and capacity, which are
what actually differentiate candidates once a topology has heterogeneous backup quality.
The greedy assignment picks $\arg\max_c \mathrm{score}(p,c)$ for each primary in turn,
then applies a load penalty to the chosen host ($\mathrm{cap} \mathrel{-}= 20$;
$\mathrm{health} \mathrel{*}= 0.95$) before moving to the next primary. This penalty is
the mechanism that spreads load across the backup pool without any learning component.

\subsection{Optimal: Capacity-Constrained Hungarian Assignment}

To obtain an upper bound the heuristic and RL policy can be judged against, we solve the
assignment problem exactly. Each backup $h$ is duplicated into
$k = \lceil |P| / |H \setminus P|\rceil$ capacity-constrained columns; the cost matrix
entry for primary $p$ and column $j$ (backup $h$) is $-\mathrm{score}(p,h)$, or a large
penalty if $h$ is infeasible for $p$. We solve this exactly via the Hungarian
algorithm~\cite{kuhn1955hungarian} (\texttt{scipy.optimize.linear\_sum\_assignment}~\cite{virtanen2020scipy}),
yielding a globally optimal assignment under the capacity constraint, something no
greedy or online method can guarantee in general.

\subsection{RL: PPO with Invalid-Action Masking}

We train a Proximal Policy Optimization~\cite{schulman2017proximal} agent
(\texttt{stable-baselines3}~\cite{raffin2021stable} over a
\texttt{gymnasium}~\cite{towers2024gymnasium} environment) on the same scoring objective
as the heuristic. One episode assigns a backup to every primary in sequence, under one
random resource realization; the observation is each host's
$[\mathrm{health}, \mathrm{cap}/\mathrm{cap}_{\max}, \mathrm{cpu}, \mathrm{storage}]$
concatenated with a one-hot encoding of the currently-active primary, and the action
space is $\mathrm{Discrete}(|H|)$. The reward is $\mathrm{score}(p,c)$ for a feasible
choice, an overload penalty proportional to how many primaries already share that
backup, and a large fixed penalty ($-10$) for an infeasible choice, so invalid actions
are discouraged \emph{during training}, not merely corrected at inference time as in a
naive post-hoc-masking design. A fresh random resource realization is drawn every
episode so the learned policy generalizes across resource realizations rather than
memorizing one instance. At inference, the deterministic policy is rolled out once per
primary, falling back to the best-scoring feasible candidate in the rare case the policy
still selects an infeasible action.

\section{Experimental Methodology}
\label{sec:methodology}

\subsection{Testbed: RPC-Isolation, Not Physical Mininet}

We measure backup-selection quality by driving the \emph{real, unmodified} \texttt{Backup}
and \texttt{Primary} 2PC classes from DEFT's implementation directly over XML-RPC, with
each backup host running as its own OS process on localhost. This is a deliberate
departure from a physical Mininet network path, which we attempted first: the
development environment's kernel lacked the \texttt{openvswitch} kernel module and the
\texttt{htb} traffic-control queueing discipline, no SDN controller was included in the
original repository, and, decisively, \texttt{TCLink} bandwidth throttling did not
engage on the available kernel, so there was no real resource constraint for contention
to manifest against over the physical network path. The RPC-isolation testbed, by
directly exercising the actual backup RPC server under controlled concurrent load, gives
a more direct and reproducible measurement of the contention mechanism in question, at
the cost of not validating full end-to-end network behavior (switching, real link
bandwidth, packet loss); see \S\ref{sec:threats}.

Each primary fires a \emph{burst} of simultaneously in-flight RPC calls rather than one
sequential call-then-wait stream, matching how concurrent primaries would load a shared
backup in production. Three implementation pitfalls were identified and corrected during
harness development: (1) running backup servers as threads within one process shares a
GIL, confounding the very contention effect being measured, so servers now run as
separate OS processes; (2) creating a fresh RPC connection per call forces a new TCP
handshake every time, dominating measurement with connection-thrash noise rather than
queueing/RPC latency, so each burst worker keeps one persistent connection for all its
calls, with retry-with-jittered-backoff on transient connection resets; and (3) an early
version built a single host-resource context per seed and passed that same object to every
method, but the heuristic and RL selectors apply an in-place load-decay penalty to each
host they pick, so any method evaluated after them scored against an already-depleted
context and its measured mapping depended on execution order, so each method now receives
its own copy of the context.

\subsection{Scenarios}

\textbf{Homogeneous (9 hosts).} DEFT's real reference topology, 5 primaries, synthetic
resource values drawn independently per random seed with no engineered heterogeneity.

\textbf{Scaled heterogeneous (16, 32, 128 hosts).} Synthetic star topologies at
increasing scale (10/20/80 primaries; 6/12/48 backup-eligible hosts), with
$\lfloor|H \setminus P| / 3\rfloor$ of the backup-eligible hosts deliberately degraded
(health $=0.05$, capacity ratio $\approx 0.03$, plus an artificial +50\,ms per-call
server-side delay simulating a genuinely overloaded machine). This isolates whether
feature-aware methods avoid known-bad hosts, independent of load-balancing alone, and
whether the finding holds as the candidate pool grows by roughly an order of magnitude.

\subsection{Statistical Methodology}

We draw multiple independent topology/resource realizations (context seeds) rather than
repeating trials of one fixed instance, since repeated trials of a single instance only
capture RPC-timing noise, not whether a result generalizes across problem instances;
reported numbers aggregate across all (context seed $\times$ trial) combinations.
Per-trial method execution order is randomized so no method is systematically favored or
disadvantaged by background system load at a particular point in a long run. We use the
two-sided Mann-Whitney $U$ test for pairwise significance and rank-biserial correlation
as an accompanying effect size, since with sample sizes in the tens of thousands,
$p$-values are almost always significant regardless of practical magnitude
($|r| \approx 0.1/0.3/0.5$ conventionally denote small/medium/large effects). We report
bootstrap 95\% confidence intervals on the mean (5000 resamples).

\subsection{Selection Overhead}

``Elastic scaling'' requires the selection algorithm itself to be fast: a method that
matches the optimal bound on placement quality but takes seconds to compute is a
materially worse deployment story than one that is comparably fast. Table~\ref{tab:overhead}
reports the mean wall-clock time to compute one full mapping, across all four topology
sizes (30 repeats each, first call excluded as warmup), and
Figure~\ref{fig:overhead} plots the same data on log--log axes. Even the slowest method
computes a full 128-host mapping in about 50\,ms (\texttt{rl}, 49.6\,ms mean), and every
other method in under 10\,ms, negligible relative to any realistic failure-detection interval
(typically hundreds of milliseconds to seconds in NF failure-recovery
literature~\cite{gill2011understanding,potharaju2013demystifying}). \texttt{rl} is
consistently slowest (one PPO forward pass per primary, plus framework call overhead);
its jump at 128 hosts (49.6\,ms, versus 11.3\,ms at 32 hosts) is the direct cost of the wider
$[256,256]$ network needed to fix the policy collapse described in \S\ref{sec:rl128}, on top
of the growth in primary count.
\texttt{heuristic} and \texttt{optimal} grow roughly linearly/superlinearly with host
count (the Hungarian algorithm is $O(n^3)$) but remain below 9\,ms at 128 hosts. None of
the feature-aware methods introduce a

\texttt{round\_robin}'s apparent performance at any single scale.

\subsection{Scalability Trend Continued: 128 Hosts}
\label{sec:rl128}

Table~\ref{tab:scaled128} reports the 128-host point at the original 16-host trial
count (5 context seeds $\times$ 3 trials, 200 calls/primary, burst=10) rather than a
reduced protocol, to keep this the most statistically comparable large-scale point. This
run required a benchmark-harness hardening: the original 3-attempt retry budget assumed
a worst case of roughly 10 primaries sharing one backup; at 79 primaries sharing one
backup (\texttt{concentrated}), Python's default \texttt{SimpleXMLRPCServer} accept
backlog (5) was overwhelmed badly enough that calls exhausted the retry budget and
crashed the experiment outright. We hardened this to 8 attempts with jittered
exponential backoff, recording a call that still fails after all retries as a failure
(a 10\,s sentinel latency) rather than crashing, the same robustness a real production
2PC client would need. This changes the harness's failure handling, not the backup
server under test.

\textbf{Concentrated sits at the edge of outright failure at this scale.} In the reported
run, a burst of calls against the single backup serving 79 other primaries
(\texttt{concentrated}, context seed 2) exhausted the 8-retry budget and were recorded as
failures at the 10\,s sentinel latency; the other four seeds of the same configuration
completed every call. Either way, \texttt{concentrated}'s mean latency remains more than an
order of magnitude above every other method, with p99 at roughly 19\,s of genuine queueing
delay. That whether calls fail at all swings across otherwise-identical seeds is part of the
finding: at this contention level, \texttt{concentrated}'s behavior is not merely bad but
\emph{unstable}. This is a
concrete finding about DEFT's shipped backup implementation: using Python's default
accept backlog, it cannot reliably serve roughly 79 concurrent primaries sharing one
backup even with client-side retry-with-backoff, a genuine scalability ceiling of the
implementation, not a benchmark artifact.

\textbf{Round-robin, heuristic, and optimal are practically indistinguishable at this
scale.} \texttt{round\_robin}'s mapping happens to hit zero degraded-host assignments at
128 hosts (the alphabetical-sort coincidence noted in \S\ref{sec:scale32}), so it is
not penalized here for the mechanism this scenario is designed to test. Their means sit
within about 2\% of one another (47.9, 48.1, and 49.1\,ms for \texttt{heuristic},
\texttt{round\_robin}, and \texttt{optimal}), and since these three methods' mappings are
fully determined by topology and context seed, that residual spread is RPC-timing noise
rather than a quality difference. This is not a reversal of our core claim but its
clearest illustration: round-robin's outcome is uncontrolled, scoring badly at 16/32
hosts and well at 128 hosts purely by naming coincidence, whereas heuristic and optimal
avoid degraded hosts \emph{by construction} regardless of scale, naming, or noise.

\textbf{RL: an attempted fix, with partial success.} The original
\texttt{rl\_model\_scaled128} (400,000 timesteps, \texttt{stable-baselines3}'s default
entropy coefficient of 0 and a $[64,64]$ network) converged to a near-degenerate policy:
across the five context seeds it used only 1--5 distinct backups out of 80, funnelling
almost every primary onto the same single host (\texttt{w101}) and triggering the same
accept-backlog failure as \texttt{concentrated}. Since PPO's entropy bonus is zero by
default, nothing discourages a policy from locking onto one action early once it looks
decent on average, a plausible root cause, compounded by a $[64,64]$ network's limited
capacity to represent a policy conditioned on which of 80 one-hot-encoded primaries is
active. We made two escalating retraining attempts: an intermediate one (entropy
coefficient $0.01$, network $[128,128]$, 600k timesteps) that improved the spread only
partially, and the fix that produced the reported model (entropy coefficient $0.02$,
network $[256,256]$, larger rollout and batch sizes, 1M timesteps, the \texttt{rl} row of
Table~\ref{tab:scaled128}). Figure~\ref{fig:rlspread} contrasts the degenerate baseline
with this final model, the two configurations shipped as reproducible checkpoints.

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{figures/fig_rl_spread.pdf}
\caption{Distinct backups used by the PPO policy across the 80 primaries at 128
hosts, for the degenerate baseline and the final fixed model of \S\ref{sec:rl128} (the
two configurations shipped as reproducible checkpoints). Bar height marks the midpoint

\label{fig:rlspread}
\end{figure}

The final fix repairs one of the policy's two failings completely and the other only in
part. On host quality it is total: \emph{zero} degraded-host assignments across all 5
seeds (0 of 400), matching heuristic/optimal exactly and generalizing across every seed
tested. On load balancing it improves markedly but stops short of the feature-aware
baselines. The policy spreads the 80 primaries across 24--30 distinct backups depending on
seed, against the heuristic's 74--76, and in the tighter seeds it still funnels as many as
28 of the 80 onto one favoured host (peak per-backup load ranges 9--28 across seeds),
versus heuristic/optimal's near-uniform 1--2 per backup (most of the heuristic's backups
carry exactly one primary). This concentration shows up only in the tail: \texttt{rl}'s
\emph{median} latency (26.6\,ms) is in fact the lowest of any method in
Table~\ref{tab:scaled128}, but its hot host drives mean 457.86\,ms and p99 7178.12\,ms,
roughly $7$--$10\times$ worse than heuristic/optimal/round-robin, though still far better
than the original collapse, which crashed the harness entirely.

That split is this paper's sharpest finding about RL at scale, and it is a mixed one.
The same policy that learns host-quality discrimination \emph{perfectly} learns
load-balancing precision only partially: it spreads far better than the collapsed
baseline, yet still leans on a handful of favoured hosts. The mechanism is visible in the
reward: its health and capacity terms label which hosts are bad, and the network learns
that completely, but nothing penalizes concentration directly, and the implicit
health/capacity decay never fully substitutes for it, so a few labelled-good hosts can
absorb a disproportionate share of the flow set without the policy paying enough for it.
We report this as a precise,
mechanistic characterization of an unresolved limitation rather than a vague ``RL doesn't
scale'' claim: the two properties are learned at radically different rates as the action
space grows. Reward shaping that directly penalizes load concentration is the natural
next step and was not attempted here.

\subsection{Throughput and Failure Rate}

Tables~\ref{tab:throughput9} and~\ref{tab:throughput16} complement per-call latency with
the other two metrics DEFT's original evaluation reports: throughput and packet drop. We
measure each primary's burst workers for a fixed 3-second wall-clock window (rather than
a fixed call count) and report successful calls/second and the percentage of calls that

underlying phenomenon (an overloaded backup failing to keep up with demand), not a

therefore visible from the throughput side, not only from tail latency.

The degraded-host effect is a subtler matter, and the honest characterization is that
aggregate throughput resolves it only partially. In the reported run \texttt{optimal} and
\texttt{rl} each significantly out-throughput \texttt{round\_robin} ($r = 0.63$ and $0.65$,
$p < 0.004$), consistent with \texttt{round\_robin} pairing 2 of its 10 primaries with a
degraded backup in every seed; yet \texttt{heuristic} vs.\ \texttt{round\_robin} does
\emph{not} reach significance ($p = 0.38$), despite \texttt{heuristic} avoiding degraded

fragility: only 2 of \texttt{round\_robin}'s 10
primaries are actually paired with a degraded backup, and their reduced individual
throughput is averaged into the other 8 primaries' normal throughput at the aggregate
level, leaving a signal small enough that run-to-run noise decides the verdict. Tail
latency is dominated by exactly the slow calls that throughput's mean-based aggregation
smooths over, and resolves the same effect consistently at every scale we tested. This
is why we treat latency as the primary metric throughout and throughput as corroborating
rather than replacing evidence: throughput reliably resolves gross contention, but only
marginally resolves the finer degraded-host effect that this paper is actually about.

\section{Threats to Validity}
\label{sec:threats}

\textbf{RPC-isolation testbed, not the physical Mininet network.} As described in
\S\ref{sec:methodology}, we exercise DEFT's real backup RPC server directly rather than
over a physical/emulated network path, after the available Mininet environment could not
provide a genuine bandwidth constraint for contention to manifest against. This gives a
direct, reproducible measurement of the contention mechanism at the cost of not
validating full end-to-end network behavior (switching, real link bandwidth, packet
loss).

\textbf{Single physical machine.} All ``hosts'' are OS processes on one machine;
OS-level scheduling noise is a real, visible component of tail latency. Multi-seed
aggregation and large sample sizes mitigate but do not eliminate this.

\textbf{Synthetic resource values.} Health, capacity, CPU, and storage availability are
drawn from configured ranges, not measured from real workload telemetry.

\textbf{RL requires scale-dependent hyperparameters.} A PPO policy's observation/action
space is fixed to a given host count; a differently-sized topology needs a freshly
trained model, and as shown in \S\ref{sec:rl128}, the hyperparameters that suffice at 16
and 32 hosts produce a degenerate policy at 128 hosts. We identify the precise remaining
limitation as load-balancing precision, not host-quality discrimination, but a reward
function directly penalizing load concentration was not attempted. The reported RL numbers
are moreover tied to the specific trained checkpoints we release: retraining even at the
same seed under a different \texttt{stable-baselines3}/\texttt{PyTorch} version, or at a
different host count, yields a different policy, so the RL rows describe the behavior of
these released models rather than a version-independent guarantee of the method.

\textbf{Round-robin's degraded-host exposure is coincidental, not stable.}
\texttt{round\_robin}'s cycling interacts with Python's alphabetical host-name sort in a
way that happens to hit the degraded range at 16/32 hosts but misses it entirely at 128
hosts. Conclusions about round-robin's relative latency should be read as
``uncontrolled/coincidental exposure to bad hosts,'' not a stable ``$\sim$20\% worse''
rate; the consistent, load-bearing claim is that heuristic/optimal/RL avoid degraded
hosts by construction in every scenario tested, a guarantee round-robin cannot offer in
any of them.

\textbf{Retry-policy inconsistency across scale points.} The 128-host run required a
harness hardening (3 to 8 retry attempts) after the original budget crashed under
80-primary contention. The 9/16/32-host results predate this fix but never exhausted the
original budget in practice, so they should be unaffected, but were not re-run under the
identical harness version.

\textbf{Scale sweep is three points, not a continuous curve}, with the 32-host point run
at a reduced trial count (3 seeds $\times$ 2 trials $\times$ 150 calls vs.\ 5 $\times$ 3
$\times$ 200 at 16 and 128 hosts) to keep it tractable. The qualitative findings hold at
all three points, but a continuous sweep with fully matched trial counts would be needed
for a rigorous asymptotic scalability claim.

\textbf{Multi-seed generalization covers resources, not topology structure.} Our
context-seed sweep varies synthetic resource draws independently per seed, but the
underlying star-topology graph shape is deterministic for a given host/primary count; a
genuinely different graph shape (multiple hubs, uneven fan-out) is untested.

\section{Conclusion and Future Work}
\label{sec:conclusion}

Every major NF state-replication system we surveyed (OpenNF, Split/Merge, StatelessNF,
S6, Pico Replication, FTMB, REINFORCE, and DEFT) treats backup-node assignment as
solved by fiat rather than as a decision with measurable consequences. We have closed
this gap concretely with iDEFT, designing and rigorously evaluating three backup-selection
strategies (a multi-criteria heuristic, an exact Hungarian-optimal bound, and a PPO
policy) against DEFT's own static mapping and three naive baselines, by driving DEFT's
real, unmodified 2PC implementation under controlled contention across four topology
scales with statistically rigorous, multi-seed testing. Feature-aware methods reliably
avoid degraded backup hosts and substantially reduce tail latency once hosts differ in
quality, a well-designed deterministic heuristic tracks the exact optimal bound closely
at every scale we tested, and reinforcement learning matches this performance up to 32
hosts but requires careful, scale-dependent hyperparameter tuning to avoid a policy
collapse at 128 hosts; even after that fix, it still trails the heuristic on
load-balancing precision specifically, not on host-quality discrimination. We report
this as a precisely characterized, currently open limitation rather than a solved
problem or a silently-buried failure.

Future work includes: reward shaping that directly penalizes load concentration for the
RL policy at large scale; validating these findings over a physical or emulated network
path with genuine bandwidth constraints; extending the multi-seed evaluation to vary
topology structure, not just resource values; and a continuous scalability sweep with
matched trial counts across an uninterrupted range of host counts.
