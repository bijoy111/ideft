A Bare-Metal Evaluation and Its Measurement Pitfalls}

\begin{abstract}
Fault-tolerant Network Function Virtualization (NFV) systems replicate a
network function's state to a backup instance, but do not say which host
should receive it; work that allocates backups optimizes cost and
availability. We measure what the choice of backup host is worth to
replication latency. An exact assignment, a greedy heuristic and two learned policies
are compared with random, round-robin and hashing placement, driving the
replication call of DEFT's backup server on bare metal: 128 backups on
dedicated cores, with degraded hosts slowed by the kernel. Placement that ignores host state sends
$10$--$12.5\%$ of calls to a degraded backup, costing a fifth of mean latency
and raising p99 $2$--$2.5\times$ at 16, 32 and 128 hosts. A greedy heuristic
stays within $1.7$\,ms of the exact assignment; with equivalent hosts no
method beats random. These runs tell selectors which hosts are degraded, so
they measure what avoidance is worth, not detection. Detection is examined on
the selected mappings only: with partial symptoms,
resource gauges miss a host degraded in its network path, and measured
round-trip time is the strongest single signal, in a model where every failure
adds delay. Three measurement pitfalls
generalize. A connection-per-call RPC stack with a short accept queue biases
the measured effect in a direction set by workload concentration. A fixed layout
of degraded hosts lets a policy that reads no host state appear to avoid them.
And a degradation model that separates degraded hosts on every feature cannot
rank scoring functions. Backup selection should read host state, measured
latency above all, but need not be exact.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Network Function Virtualization (NFV) replaces dedicated hardware middleboxes with
virtualized network functions (NFs) running on commodity servers, enabling elastic
scaling and fault tolerance that fixed hardware cannot provide~\cite{han2015network}.
A stateful NF's correctness depends on preserving per-flow and global state across
failures and load-driven scaling events. The dominant approach to fault tolerance for
stateful NFs is \emph{replication}: a primary NF instance forwards its state updates to
one or more backup (secondary) instances, which take over processing if the primary
fails~\cite{rajagopalan2013pico,sherry2015rollback,kulkarni2018reinforce}. DEFT~\cite{shahriyar2023deft}
extends this line of work with a distributed, controller-free two-phase-commit (2PC)
protocol that achieves both elastic scaling and fault tolerance with strong consistency
on global state updates, without the single point of failure a central controller
introduces.

\subsection{The Gap: Which Host Receives the State}

The systems that replicate NF state do not treat the choice of backup host as a
decision. REINFORCE~\cite{kulkarni2018reinforce} designates a predecessor node
and a backup node per NF without describing a selection rule.
OpenNF~\cite{gember2014opennf}, Split/Merge~\cite{rajagopalan2013split},
StatelessNF~\cite{kablan2017stateless} and S6~\cite{woo2018elastic} describe how
state is migrated or shared once a target instance is known, not how that target
is chosen. In DEFT's reference implementation the consequence is concrete: the
static mapping shipped for its 9-host evaluation topology places 3 of 5
primaries on one backup host, with no reference to load or
health~\cite{shahriyar2023deft}.

A separate literature does allocate backups for virtual network functions
(\S\ref{sec:related-backup}). It decides how many backups to provision and where,
so that a service meets an availability target at the lowest resource cost, and
it is evaluated analytically or in simulation. It does not ask what the state of
the chosen host does to the replication path of a running system: how much
slower replication becomes when the backup is degraded or shared, and what a
selector must observe to avoid that. That is the question here. We scope the
work to replication for fault tolerance. Choosing a target for state migration
during elastic scaling is a related decision that our formulation could extend
to, and we do not evaluate it.

\subsection{Contributions}

Scoring candidate hosts and assigning backups accordingly is simple to do.
Showing that it beats an arbitrary assignment is harder, because a placement
experiment claims that a latency difference was caused by the choice of backup,
and several properties of the measurement can produce or hide such a difference
on their own. The paper makes three contributions.

\begin{enumerate}
\item \textbf{A greedy heuristic matches the exact assignment and beats
order-based placement, measured on bare metal.} We formulate backup selection
as a capacity-constrained assignment under a multi-criteria score and compare
an exact assignment, a greedy heuristic and two learned policies against
order-based and hash-based baselines (\S\ref{sec:methods}). On 128 backups
across ten nodes, each on a dedicated physical core, with degraded hosts
impaired by the kernel (\S\ref{sec:methodology}), the greedy heuristic is
within $1.7$\,ms of the exact assignment in mean latency at 16, 32 and 128
hosts, so neither an exact solve nor a learned policy is needed. Round-robin
is $6.7$--$10.1$\,ms slower than the exact assignment and $6.1$--$9.8$\,ms
slower than the heuristic, about a fifth of its mean, with p99 higher by a
factor of $2$ to $2.5$: that is the measured cost of sending $10$--$12.5\%$ of
calls to a degraded backup. With homogeneous hosts no method
separates from random (\S\ref{sec:results}).

\item \textbf{Which signal carries the avoidance, examined structurally.} We
examine whether degradation can be detected under a model with five failure
kinds and continuous severity, scored on the selected mapping. A score restricted to resource gauges
and topology-derived latency selects a host degraded only in its network path;
with measured round-trip time in its place the default weights go from about
$3\%$ of assignments on degraded hosts to under $1\%$. Measured latency is the
strongest single signal in this model, in which every failure kind adds some
delay and the measurement is exact and current (\S\ref{sec:weights}).

\item \textbf{Three measurement pitfalls, each with a control.} A
connection-per-call RPC stack with a short accept queue biases the measured
placement effect: holding everything else fixed, lengthening the queue takes the
measured cost of concentrating backups from $7.5\times$ to $35\%$ at 128 hosts
and \emph{widens} the gap between placement methods at 16, so no constant
correction removes the bias (\S\ref{sec:p99}). A contiguous block of degraded
hosts lets a policy that walks hosts in order score perfect avoidance by never
reaching the block (\S\ref{sec:degconstruct}). And a degradation model that
pins every feature of a degraded host to an extreme cannot rank scoring
functions: any weight on any host feature scores perfectly, and with a fixed
layout so does a score that reads nothing (\S\ref{sec:binarymodel}).
\end{enumerate}

\subsection{What Is Measured and What Is Not}
\label{sec:scope}

Three limits shape how the contributions should be read, and we state them
here and not only among the threats.

\emph{The latency runs supply the selectors with the truth.} A degraded host's
features are reported exactly and at once, so a state-aware selector avoids it
by construction. That no call from the heuristic or the exact assignment
reaches a degraded backup is therefore a premise of contribution~1 and not a
result. The results are what that avoidance is worth, and that a greedy pass
obtains all of it.

\emph{Detection is not measured on the testbed.} Contribution~2 counts degraded
assignments in the mappings each scoring function produces. We have not yet run
the realistic degradation model on the testbed with probed round-trip times and
noisy, delayed telemetry. That experiment would join the two halves of the
paper, and it is the principal item of future work (\S\ref{sec:threats}).

\emph{The exact assignment bounds the score, not latency.} It maximizes the
total score under a cap on primaries per backup. The score is a proxy for
latency. Measurement supports the proxy under the binary model, where the
score-maximizing mapping is also the fastest measured one
(Table~\ref{tab:scales}); under the realistic model it is supported
structurally only. ``Matches the exact assignment'' therefore means matches the
best mapping this score can express, not the latency optimum. The bound is
also tied to a regime: in the measured runs backups outnumber primaries, where
a perfect spread always exists. \S\ref{sec:oversub} examines the oversubscribed
case structurally and finds that the cap, and not the greedy pass, is what
fails there.

\section{Related Work}
\label{sec:related}

\subsection{Elastic and Fault-Tolerant State Management}

NF state management for elastic scaling follows two strategies. State migration
moves NF state between instances. Split/Merge~\cite{rajagopalan2013split} splits state
into per-flow and global parts; global updates merge periodically and stay eventually
consistent, but in-flight traffic can be dropped during migration. OpenNF~\cite{gember2014opennf}
offers move, copy, and share operations for different consistency levels. Both systems need a central controller to coordinate migration. 

Migration avoidance instead decouples state from processing. StatelessNF~\cite{kablan2017stateless,szalay2019industrial} keeps state in a remote data store, adding per-packet latency and a single point of failure. S6~\cite{woo2018elastic} spreads state across a Chord-like key/object layer~\cite{stoica2003chord}, reducing, but not eliminating, migration through caching and
replication.

NF fault tolerance instead relies on replication and checkpointing. Pico Replication~\cite{rajagopalan2013pico} checkpoints frequently~\cite{plank1994libckpt} for loss-free recovery, but does not handle in-flight packets arriving during a checkpoint. FTMB~\cite{sherry2015rollback} checkpoints infrequently and logs and replays packets instead, favoring throughput over checkpoint frequency. REINFORCE~\cite{kulkarni2018reinforce} combines both: packets are buffered at a predecessor node and replayed to a backup on failure, with lazy
checkpointing except for non-deterministic packets~\cite{cachin2016non}, which force a
strict checkpoint. All three assume a backup already exists for each primary.

DEFT~\cite{shahriyar2023deft} spans both strands: one distributed 2PC protocol handles
elastic scaling and fault tolerance together, with no central controller
(unlike~\cite{gember2014opennf,rajagopalan2013split}). It shares the gap of the fault-tolerant systems: backup assignment is a bookkeeping step in its Failure Detection Unit, a static map.

\subsection{Backup Allocation and Replica Selection}
\label{sec:related-backup}

\textbf{Backup allocation for VNFs.} Allocating backups to virtual functions is
studied as a provisioning problem. Kanizo et al.~\cite{kanizo2017optimizing}
share a small pool of backup servers among many middleboxes and find assignments
that reach a target survival probability with the fewest servers.
GREP~\cite{fan2015grep} and RABA~\cite{zhang2019raba} decide which functions of
a service chain receive backups, and how many, to meet a reliability requirement
within a resource budget. FTC~\cite{ghaznavi2020ftc} avoids dedicated backups by
replicating each function's state to the functions that follow it in the chain,
so the chain order fixes the target. These works answer how many backups and for
which function. Their objectives are availability and resource cost, the backup
hosts are interchangeable within a capacity model, and the evaluations are
analytical or simulated. None measures how the state of the selected host
affects replication latency in a running system, which is the subject here.
Closer in spirit, Avgeris et al.~\cite{avgeris2023reinforcement} reposition VNFs
after a failure or contention event has been detected, a reactive remedy,
whereas we choose a backup when replication is established; and Kibalya et
al.~\cite{kibalya2021reinforcement} place stateful VNFs using the primary's own
execution state, not a relationship between a primary and a distinct backup.

\textbf{Replica placement and selection in storage.} Outside NFV, which node
holds or serves a copy is a first-class decision. CRUSH~\cite{weil2006crush}
computes failure-domain- and weight-aware placement without a central lookup
table, and Dynamo~\cite{decandia2007dynamo} spreads replicas by consistent
hashing with capacity-aware preference lists. Their mechanism, decentralized
weighted hashing, carries over directly to NF backups, so we adopt it as a
baseline family (\S\ref{sec:hrw}). C3~\cite{suresh2015c3} selects among existing
replicas per request, ranking them by measured response time and queue length
fed back from the servers. Our finding that measured latency, and not a resource
gauge, is the signal that reveals a degraded backup (\S\ref{sec:weights}) agrees
with C3's premise in a different setting: C3 chooses a replica to read from on
every request, while a backup assignment is held for many replication calls and
changing it costs a state transfer.

\textbf{Position of this work.} We do not claim to be the first to choose
backups by criteria. To our knowledge, what has not been reported is a
measurement on a running NF replication system of what the backup host's state
costs in replication latency, together with the conditions under which such a
measurement can be trusted.

\subsection{Reinforcement Learning for NFV Resource Management}

Reinforcement learning is the usual proposal for NFV placement, almost entirely
for primary placement, scaling or embedding. Cand-RL~\cite{santos2022reinforcement}
uses PPO for availability-aware service function chain placement, and
DDQN-VNFPA~\cite{pei2019optimal} uses Double Deep Q-Networks for VNF placement.
Two surveys, on RL for virtual network embedding~\cite{lim2023reinforcement} and
for network slice scaling and placement~\cite{saha2023deep}, catalogue those
sub-problems; backup selection appears in neither. We therefore include learned
policies as a comparison a reader will expect (\S\ref{sec:rlmethod}).

\section{Problem and Methods}
\label{sec:methods}

\subsection{Problem and Features}

Let $H$ be the set of hosts and $P \subseteq H$ the hosts currently acting as
primaries. For each primary $p \in P$ we choose one backup $b \neq p$. One
definition of the backup pool is used throughout the paper: \emph{every host
except the primary itself is a feasible backup for it}, including hosts that are
primaries for other flows. The only exclusions are infrastructure hosts (the
client and the stamper), which exist in DEFT's 9-host reference topology and not
in the scaled topologies. At 16, 32 and 128 hosts with 10, 20 and 80 primaries,
each primary therefore has 15, 31 and 127 candidates.

Each candidate host $h$ carries six features. Four describe the host: health
$\mathrm{health}(h) \in [0,1]$, remaining capacity $\mathrm{cap}(h)$ out of
$\mathrm{cap}_{\max}(h)$, CPU availability and storage availability. Two
describe its path from $p$: hop count and latency. The score of
\S\ref{sec:heuristic} uses four of the six (health, capacity ratio, latency and
hop count); the learned policies observe the four host features
(\S\ref{sec:rlmethod}).

Host features are synthetic. Per host and per random seed they are drawn
independently as $\mathrm{cap}_{\max} \sim \mathcal{U}\{50,\dots,100\}$ with
$\mathrm{cap}$ initialised to $\mathrm{cap}_{\max}$,
$\mathrm{health} \sim \mathcal{U}[0.5,1.0]$, and CPU and storage availability
each $\sim \mathcal{U}[0.4,1.0]$. One such draw is a \emph{context seed}.
Topology latency is $1.5$\,ms per hop. The latency feature is either this
topology-derived value or a \emph{measured} one, which adds whatever delay the
candidate is currently contributing, as an active round-trip-time probe would
observe; \S\ref{sec:weights} shows that the difference matters.

\textbf{What the features stand for.} Each feature corresponds to a signal an
NFV orchestrator already exposes. Health maps to a composite liveness score such
as failure-detector confidence or a readiness probe. The capacity ratio maps to
headroom in the NF's dominant scaling resource, for instance free
connection-tracking or NAT-binding slots. CPU and storage availability map to
hypervisor utilisation counters, hop count to the controller's topology view,
and measured latency to active RTT probing. Driving selection from live
telemetry is future work (\S\ref{sec:threats}).

\subsection{Baselines}

\textbf{Concentrated.} Every primary is assigned the same backup (the first
feasible host). This is the worst case for load and generalizes the tendency of
DEFT's shipped mapping to place several primaries on one host.

\textbf{Random.} A uniformly random feasible backup per primary, seeded.

\textbf{Round-robin.} Cycles through the lexicographically sorted host list,
skipping a candidate only when it is the primary itself. It balances load and
reads no host state.

\textbf{Rendezvous and consistent hashing.} \emph{Plain rendezvous hashing
(HRW)} assigns each primary the feasible backup with the highest hash weight
$\mathrm{hash}(p,c)$. It needs no coordinator and spreads load in expectation,
and it reads no host state. \emph{Weighted HRW} multiplies the hash weight by
$\mathrm{health}(c)\cdot\mathrm{cap}(c)/\mathrm{cap}_{\max}(c)$, in the spirit
of CRUSH and Dynamo node weights, so it reads host state while remaining
decentralized. \emph{Weighted consistent hashing} is a Dynamo-style ring with
virtual nodes in proportion to the same weight; a host whose weight rounds to
zero places none and is never selected. None of the three propagates load
between primaries, so they spread load only statistically.

\textbf{Static.} The hand-assigned mapping DEFT ships for its 9-host topology.
It exists only at that size and appears only in \S\ref{sec:single}.

\subsection{Greedy Heuristic}
\label{sec:heuristic}

For each primary, taken in a fixed order, the heuristic scores every feasible
candidate $c$ as
\begin{equation}
\label{eq:score}
\begin{split}
\mathrm{score}(p, c) ={}& w_h \cdot \mathrm{health}(c) + w_k \cdot \frac{\mathrm{cap}(c)}{\mathrm{cap}_{\max}(c)} \\
&- w_\ell \cdot \hat\ell(p,c) - w_d \cdot \hat{d}(p,c)
\end{split}
\end{equation}
where $\hat\ell$ and $\hat{d}$ are the latency and hop count from $p$ to $c$,
min-max normalized over $p$'s candidates. The weights are
$(w_h, w_k, w_\ell, w_d) = (0.35, 0.35, 0.20, 0.10)$. We chose them before
running any experiment, on the expectation that health and capacity would
separate candidates, and did not tune them afterwards. \S\ref{sec:weights} tests
that expectation and finds it wrong in an informative way: it is the latency
term that carries avoidance once degradation is partial. The heuristic picks
$\arg\max_c \mathrm{score}(p,c)$, then applies a load penalty to the chosen host
($\mathrm{cap} \mathrel{-}= 20$; $\mathrm{health} \mathrel{*}= 0.95$) before the
next primary. The penalty is what spreads load across the pool.

\subsection{Exact Assignment}
\label{sec:optimal}

To bound what any method using this score can achieve, we solve the assignment
exactly. Each host $h$ is expanded into
$k = \lceil |P| / |H| \rceil$ columns, one per primary it may back. The cost of
assigning primary $p$ to a column of $h$ is $-\mathrm{score}(p,h)$, or a fixed
penalty of $10^6$ when $h = p$. Hosts outnumber primaries at every scale we
evaluate, so $k = 1$: the solver assigns each primary a distinct backup, with 10,
20 and 80 distinct backups at the three scales and a maximum load of one. The
measured results are therefore all from the regime in which a perfect spread
exists; \S\ref{sec:oversub} restricts the pool so that $k = 2$. We
solve it with the Hungarian algorithm~\cite{kuhn1955hungarian} as implemented in
\texttt{scipy.optimize.linear\_sum\_assignment}~\cite{virtanen2020scipy}.

Two qualifications apply wherever this method appears. It is \emph{exact for the
score} under a one-backup-per-host constraint; it is not optimal for latency,
which the score only approximates. We therefore call it the exact assignment and
label it \texttt{exact}. And it needs the complete cost matrix at one party,
which is at odds with DEFT's controller-free design, so we use it as a bound and
not as a deployment candidate.

\subsection{Learned Policies}
\label{sec:rlmethod}

We train two reinforcement-learning agents on the same objective: Proximal
Policy Optimization (PPO)~\cite{schulman2017proximal} and a Deep Q-Network
(DQN)~\cite{mnih2015human}, both from
\texttt{stable-baselines3}~\cite{raffin2021stable} over
\texttt{gymnasium}~\cite{towers2024gymnasium}. The two differ in update rule
(on-policy actor-critic against off-policy value learning) and in exploration
(entropy bonus against $\epsilon$-greedy), and share the environment, reward and
inference path. An episode assigns a backup to every primary in sequence under
one context seed. The observation is each host's
$[\mathrm{health}, \mathrm{cap}/\mathrm{cap}_{\max}, \mathrm{cpu},
\mathrm{storage}]$ concatenated with a one-hot encoding of the active primary,
and the action space is $\mathrm{Discrete}(|H|)$. The reward is
$\mathrm{score}(p,c)$, less $2(\ell-1)$ when the choice makes host $c$ the
backup of an $\ell$-th primary, less $10$ for an infeasible choice. Each host
count needs its own trained model.

\section{Testbed and Methodology}
\label{sec:methodology}

\subsection{Bare-Metal Testbed}
\label{sec:testbed}

The testbed is eleven bare-metal CloudLab nodes at the Utah cluster
(\texttt{c6525-25g}: one 16-core AMD EPYC 7302P, 128\,GB, 25\,GbE, Ubuntu
22.04). Ten nodes carry the 128 backup servers, thirteen per node except the
last, and the eleventh runs the client alone. Each server is launched under
\texttt{taskset} on a core of its own. Hyperthread siblings on this part pair as
$(0,16), (1,17), \dots$, so logical CPUs $2$--$14$ are thirteen distinct
physical cores and no two servers share one core's two threads. The provisioning
tool records the intended core in a manifest, and a verification pass reports
the affinity each server actually holds and the port it answers on. All
replication traffic crosses the 25\,GbE experiment LAN; the control network is
not used for measurement.

\subsection{System Under Test}
\label{sec:sut}

Each backup is an instance of DEFT's \texttt{Backup} class from its public
implementation: a Python \texttt{SimpleXMLRPCServer}, single-threaded, speaking
HTTP/1.0. The client issues the call DEFT's primary makes to replicate state,
\texttt{update\_state(state)}, in bursts of ten simultaneously in-flight calls
per primary, 200 calls per primary per run. Four facts bound what the resulting
latencies mean, and we state them here because the phrase ``DEFT's backup''
would otherwise claim more than was measured.

\emph{Only the replication call is driven.} The prepare and commit exchange of
DEFT's 2PC, its failure detection and its data path are not exercised.

\emph{The call does no work at the backup.} As shipped,
\texttt{update\_state} prints the state and returns; the code that would persist
it is commented out. Our harness registers an equivalent handler without the
print. Every latency in this paper is therefore the cost of connection setup,
request delivery, dispatch by a single-threaded server and the acknowledgement.
It is the latency of the replication transport and its queueing, and a lower
bound for a backup that stores what it receives.

\emph{The listen backlog is raised.} DEFT's server listens with the library
default of five. All bare-metal placement runs use 512, set on the server class
before DEFT's code constructs it, for the reason \S\ref{sec:p99} gives. Runs
with the shipped value are labelled as such.

\emph{The second transport is ours.} For the transport comparison of
\S\ref{sec:p99} we implement the same call over gRPC: one persistent HTTP/2
channel per primary and a server thread pool. This is a reimplementation of the
call's interface and not DEFT code.

The benchmark client bounds each call with a 20\,s socket timeout and retries a
transport failure up to eight times with jittered backoff. A call that exhausts
its retries counts toward the failure rate and contributes to no latency
statistic. Each method receives its own copy of the host features, because the
heuristic and the learned policies modify them as they assign.

\subsection{Scenarios and Degradation}
\label{sec:scenarios}

\textbf{Topologies.} Three scales: 16, 32 and 128 hosts with 10, 20 and 80
primaries. For the selectors the topology is a star in which every host is two
hops from every other. Hop count and topology latency are then the same for
every candidate and carry no signal, so a selector can only separate candidates
by health, capacity and, where it is used, measured latency. A multi-hub variant
with unequal hop counts is used as a check in \S\ref{sec:hrw}.

\textbf{Heterogeneous pools.} One host in eight is degraded: 2, 4 and 16 hosts
at the three scales, sampled evenly along the lexicographic host order that the
order-based baselines walk (\S\ref{sec:degconstruct} explains why). A degraded
host is slowed physically, by \texttt{tc netem} on its server's source port,
which costs $101$\,ms per call against $1$\,ms for a healthy neighbour
(\S\ref{sec:degconstruct}).

\textbf{What the selectors are told.} Under the \emph{binary} degradation model,
used for every latency measurement in this paper, a degraded host's features are
pinned to $\mathrm{health}=0.05$, $\mathrm{cap}=2$ of $\mathrm{cap}_{\max}=60$
(ratio $0.033$) and an observed delay of $50$\,ms. A degraded host is thus an
order of magnitude away from every healthy host on every feature the selectors
read, and its state is reported accurately and without delay. A selector that
reads host state will avoid such a host by construction. The latency runs
therefore answer one question, what selecting a degraded backup costs and what
avoiding it is worth, and do not test whether degradation can be detected.

\textbf{The realistic model.} Detection is examined under a second model. Each
degraded host draws a severity from $\mathrm{Beta}(1.6, 1.6)$ and one of five
failure kinds, each of which moves a different subset of the features:
\texttt{cpu\_starved} (CPU availability and health), \texttt{unhealthy} (health
only), \texttt{capacity\_exhausted} (capacity ratio only),
\texttt{storage\_pressured} (storage availability and health) and
\texttt{link\_congested} (no host feature at all). Every kind adds a delay that
grows with severity, between $0.5$ and $60$\,ms. Features a kind does not move
stay at their healthy draw, and every host whose capacity the degradation does
not set carries a baseline utilisation, so remaining capacity is a continuous
quantity that a degraded host can overlap. Results under this model are
\emph{structural}: we score the mapping a method produces and issue no RPC
calls. In structural results each seed redraws the host features, which hosts
are degraded (uniformly at random, one in eight), and their kinds and
severities.

\textbf{Structural metrics and what they mean for latency.} Where a mapping is
scored without measurement we report two quantities. \emph{Degraded
assignments} is the number of primaries given a degraded backup; its latency
consequence is the one measured in \S\ref{sec:hetero}. \emph{Peak load} is the
largest number of primaries sharing one backup. Its latency consequence on this
testbed is small until sharing is heavy (under $1$\,ms up to 16 primaries on one
backup, $35\%$ at 79; Table~\ref{tab:loadcurve}), so we read small differences
in peak load as differences in fan-in, the number of primaries that lose their
replica together if that backup fails, and not as differences in latency.

\subsection{Statistical Methodology}
\label{sec:stats}

Each bare-metal configuration is run under 5 context seeds with 3 trials per
seed. One \emph{run} is one (method, seed, trial) execution, giving 15 runs per
method. Within a trial the order in which methods execute is randomized.

\textbf{The unit of analysis is the seed.} Observations are nested, and each
level is tempting to count. Calls within a run are not independent: they share a
connection sequence, a single-threaded server and a scheduler. Pooling them
inflates $n$ into the tens of thousands; on synthetic data from two methods with
no true difference and correlated calls within runs, a Mann-Whitney test over
15{,}000 calls returns $p = 1.1\times10^{-44}$ where the run-level test returns
$p = 0.76$. Runs within a seed are not independent problem instances either: the
three trials of a seed share its host features and, for every method, its
mapping, so they repeat the RPC timing and not the instance. We therefore reduce
each run to its mean and p99 over successful calls, average those over the
seed's three trials, and compare methods by paired differences across the
\emph{five} seeds.

\textbf{What is reported.} With five pairs an exact two-sided Wilcoxon
signed-rank test cannot return less than $p = 0.0625$, so no rank test can
reject at $0.05$ at this size. We report instead the mean paired difference, its
$95\%$ confidence interval (paired $t$, four degrees of freedom) and the number
of seeds that agree in sign (Table~\ref{tab:seedlevel}). We call two methods
different when the interval excludes zero. We do not call two methods equivalent
because a test failed to reject; where the claim is similarity we give the
interval, which states how large a difference the data leave room for. Five
seeds are few. The interval assumes roughly normal seed-level differences, which
five values cannot check, and \S\ref{sec:threats} lists this among the limits.

\textbf{Mean and p99.} With the backlog at 512 no connection is refused and p99
is a latency. With the shipped backlog p99 is the kernel's SYN-retransmission
timer (\S\ref{sec:p99}); we quote it there only to show that pathology.

\subsection{Single-Machine Harness}
\label{sec:harness}

Before the testbed, the same comparison ran with every host as a process on one
8-core machine, over both transports. Those runs differ from the bare-metal ones
in four ways: hosts share cores; a degraded host is slowed by a $50$\,ms sleep
inside the server; the XML-RPC arm uses the shipped backlog of five; and the
degraded hosts are the first hosts that are not primaries, a contiguous block.
They comprise 15 runs per method on XML-RPC and 25 on gRPC (5 seeds with 3 and 5
trials) and are analysed at run level, so their $p$-values overstate the
evidence in the way described above. Identical executions on this harness differ
by up to $17$\,ms in mean, a shift common to every method, and at 128 hosts by
a factor of $4.8$, so it yields no usable latency at that scale. We use these runs for two purposes only: the
transport comparison of \S\ref{sec:p99}, where the same workload is needed on
both stacks, and a consistency check on the ordering of methods
(\S\ref{sec:single}).

\section{Threats to Validity}
\label{sec:threats}

\textbf{Host state is synthetic and, in the latency runs, accurate by
construction.} This is the main gap. Features are drawn from the ranges of
\S\ref{sec:methods} and not measured from live telemetry, and under the binary
model the selectors are handed the degraded hosts' state exactly and without
delay (\S\ref{sec:scenarios}). The latency results therefore establish the cost
of selecting a degraded backup, and not that a deployed selector would avoid
one. Telemetry that is noisy or stale will let a state-aware selector choose a
host that has just degraded; how often is not measured here.

\textbf{The realistic model is scored structurally.} \S\ref{sec:weights} counts
degraded assignments and measures no latency, and its measured RTT is exact.
The experiment that would close both this gap and the previous one is a
bare-metal run with the realistic model, RTT obtained by probing, and features
reported with noise and delay. We regard it as the most important missing
measurement.

\textbf{The replication call does no work at the backup.} DEFT's
\texttt{update\_state} returns without storing state (\S\ref{sec:sut}). The
latencies are those of transport and queueing. In particular the low cost of
sharing a backup (Table~\ref{tab:loadcurve}) is a lower bound: a backup that
applied each update would be more sensitive to load, and load balance would
matter more than it does here.

\textbf{The oversubscribed regime is not measured.} In every latency run backups
outnumber primaries. \S\ref{sec:oversub} compares the heuristic with the exact
assignment at $k = 2$ on score and structure only.

\textbf{Five seeds.} Each bare-metal configuration has five independent problem
instances. The main effects are large against their intervals and hold in every
seed, but the intervals rest on a normality assumption that five values cannot
test, and the similarity of the heuristic to the exact assignment is bounded
only to the widths reported in Table~\ref{tab:seedlevel}. Twenty or more seeds
would tighten both.

\textbf{One system, one replication path.} All measurements use DEFT's backup
server over XML-RPC, with a gRPC reimplementation for the transport comparison.
Kernel-bypass paths (DPDK, RDMA) remove the kernel networking stack and would
queue differently. Only the replication call is driven; a packet-level
evaluation over an SDN fabric, in which the RPC failure rate could be checked
against DEFT's packet-drop metric, remains to be done.

\textbf{Topologies.} Three scales, on a star and a multi-hub graph, with a
fixed ratio of primaries to hosts and of degraded to healthy hosts. In a star
the hop-count and topology-latency terms carry no signal, so the testbed runs
exercise only the health, capacity and measured-latency terms of the score.

\textbf{Learned policies.} A policy's observation and action spaces are tied to
a host count, so each scale has its own model, and the reported numbers
describe the released checkpoints. The search over configurations was targeted
and not exhaustive (\S\ref{sec:rl128}).

\textbf{Single-machine runs.} The transport comparison and the consistency
check of \S\ref{sec:single} come from a harness with shared cores, the shipped
backlog on its XML-RPC arm, a contiguous degraded block and run-level
statistics (\S\ref{sec:harness}). We use them for the shape of the latency tail
and for the ordering of methods, and not for magnitudes.

\section{Conclusion and Future Work}
\label{sec:conclusion}

NF state-replication systems specify how state reaches another host and leave
open which host it reaches, and backup-allocation work chooses hosts for
availability and cost. We measured what the choice is worth to replication
latency on a running system, and found that establishing the answer takes more
care than producing it.

\emph{Backup selection should read host state, including measured latency, but
need not solve the assignment exactly.} On a bare-metal testbed with 128 backups on dedicated
cores and degraded hosts impaired by the kernel, placement that ignores host
state sends $10$--$12.5\%$ of replication calls to a degraded backup, which
costs about a fifth of mean latency and raises p99 by a factor of $2$ to $2.5$
at 16, 32 and 128 hosts, in every seed. A greedy heuristic stays within
$1.7$\,ms of the exact assignment on mean latency, so the exact solve is a
bound and not something to deploy. That holds where backups outnumber
primaries, which is the regime we measured. Where they do not, a structural
comparison shows the greedy pass still matching the exact score among healthy
hosts, and doing better than the capped exact assignment once degraded hosts
take up part of the pool. The
advantage is specific to heterogeneous pools: with identical hosts no method
separates from random. And it is conditional on the selector knowing which
hosts are degraded, which these runs supplied. Under a model in which symptoms
are partial, a score built on resource gauges misses a host degraded only in
its network path, and measured round-trip time is the signal that recovers it,
taking the default weights from about $3\%$ of assignments on degraded hosts
to under $1\%$.

Three results concern how such a claim must be measured, and apply beyond this
system. A connection-per-call RPC stack with a short accept queue biases the
measured placement effect with a sign that depends on workload concentration:
lengthening the queue took the measured cost of concentration from $7.5\times$
to $35\%$ at 128 hosts and \emph{widened} the gap between placement methods at
16. Degrading a contiguous block of hosts lets an order-based baseline report
an avoidance it did not earn, so a comparison must report the share of each
method's calls that met the impairment. And a degradation model that separates
degraded hosts on every feature at once cannot rank scoring functions, and
with a fixed layout cannot tell a good one from one that reads nothing.

On reinforcement learning the result is modest. PPO matches the state-aware
methods to 32 hosts and at 128 sends $0$--$2\%$ of assignments to degraded
hosts while concentrating load;
DQN collapses onto two backups at that scale. Neither has headroom over a
heuristic that already matches the exact assignment.

Future work follows from the limits above. The first step is the measurement
\S\ref{sec:threats} identifies: realistic degradation on the testbed, with
probed RTT and noisy, delayed telemetry, over more seeds. The second is a
backup that stores the state it receives, under which the cost of sharing
should be re-measured. The third is the online problem. Hosts degrade, recover
and fail, and moving a replica costs a state transfer, so an assignment that is
best for a snapshot is not best over time; deciding when a re-selection repays
its migration is a question we leave to a separate study. The harness, trained
models, raw per-call records and the saved output of every run, including the
configurations that reproduce each measurement artifact, are available for
reproduction.
