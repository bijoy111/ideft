Scalability Trend: 32 Hosts

The same setup as 16 hosts, doubled (20 primaries, 12 hosts that can act as backups, 4 of them bad, same proportions). The question here: does the 16-host result still hold when there are more hosts to choose from, or did it only work because the network was small?

3 context seeds × 2 trials (reduced — see note below) 150 calls/primary, burst=8 n = 18,000 calls/method
Fewer runs at this size: 3×2×150 calls with burst=8, instead of the 5×3×200 with burst=10 used at 16 and 128 hosts, to keep the run short enough on one machine. The overall result is the same either way, but this page has less data behind it than the others, so we say so rather than pretend they match. See EXPERIMENTS.md §5.
How often each method used a bad host (out of 20 choices per seed): concentrated, heuristic, optimal, and rl again never used one, in any of the 3 seeds. round_robin used one 4 times out of 20, in every seed, the same 20% rate as at 16 hosts. One important warning: round_robin_mapping() never looks at host resources, so this is not chance. It happens because Python sorts host names as text, not numbers, and at this size that ordering lands on the bad hosts. The 128-host page shows the same accident going the other way, down to 0%. So read that 20% as "out of anyone's control", not "reliable".

What this means: the main 16-host result still holds at twice the size, so it was not just an effect of a small network. The one method that gets relatively worse as the network grows is the naive worst case (concentrated), which makes sense: putting more primaries on a single backup means a longer queue at that backup. This is a real, if modest, scaling result. The 128-host page adds a third point, eight times larger again.
