Code Walkthrough

Everything lives in backup-node-selection/code/: eight Python files plus DEFT's own 2PC classes, unchanged. This page shows how it all fits together first, then what each file does. For more detail, see IMPLEMENTATION.md.

The main flow

One design choice to know up front: the harness talks to DEFT's real backup code over local RPC instead of through a Mininet network, because the Mininet setup available to us could not actually limit bandwidth (the openvswitch kernel module was missing and TCLink throttling never took effect). Backup servers run as separate processes rather than threads, since Python's GIL would hide the very contention we are trying to measure. Each worker also keeps one open connection, because reconnecting on every call would bury the real signal under TCP handshake noise. Paper §IV explains this in full.

File by file

topology_features.py

Single source of truth for topology and resource state

Builds a networkx graph from DEFT's switch/host port map and draws the synthetic per-host resource state (health, capacity, CPU, storage) for a given context seed. Every selection method and both harnesses consume the same FeatureContext, so no method ever sees different data.

backup_selector.py

All six non-learned methods + the mapping CLI

Feasibility filtering (a backup is any host that isn't the primary itself or an infrastructure host), the multi-criteria greedy scorer (health 0.35 · capacity 0.35 · latency 0.20 · hop-count 0.10, with load-decay after each pick), and the exact capacity-constrained Hungarian assignment via scipy.optimize.linear_sum_assignment. Run it directly with --mode/--seed/--out to regenerate primary_to_secondary.json.

rl_backup_selector.py

The RL agents: gym environment, PPO and DQN training, inference

One episode gives every primary a backup in turn, using a fresh set of host resource values each time, so the policy learns the idea instead of memorising one case. The reward is the same score the heuristic uses, minus a penalty for overloading a host and a −10 penalty for an invalid pick. Pick the algorithm with --algorithm ppo|dqn; both share the same environment, reward, and inference path, so only the learner differs. PPO options: --ent-coef --net-arch --n-steps --batch-size; DQN options: --exploration-fraction --exploration-final-eps --buffer-size --target-update-interval. Always check the result with --check-collapse, which prints how many different backups the policy uses across 5 seeds, so a bad policy shows up in seconds.

rpc_contention_experiment.py

The main latency harness, which produces the numbers on the results pages

For each seed and trial it works out every method's mapping, starts one real DEFT Backup process per host, then sends bursts of overlapping RPC calls from each primary and records the time of every call to results_rpc/rpc_contention_raw.csv. The order the methods run in is shuffled each trial, so background load on the machine cannot favour any one of them. It finishes with summary tables, Mann-Whitney tests, effect sizes, and a latency-by-backup-load breakdown. Change the size with --n-hosts --n-primaries --n-degraded --rl-model.

throughput_experiment.py

Throughput / failure-rate harness

Same server setup as the latency harness, but the workers run for a fixed length of time (--duration) instead of a fixed number of calls. It reports successful calls per second and the share of calls that fail even after retries, which are the two measures DEFT's own paper uses.

selection_overhead.py

How long does selection itself take?

Times how long each method takes to work out one full mapping, 30 times over, with the first call skipped as a warm-up, at all four network sizes, loading the right trained RL model for each. It answers the question "is the smarter choice too slow to use?". See the Overhead page for the answer, which is no.

weight_sensitivity.py

Are the heuristic's weights and decay mechanics principled?

Sweeps all 287 scoring-weight configurations (a 0.1-step grid over the 4-simplex plus the published default) across the 9/16/32/128-host topologies, 5 seeds each, scoring each structurally — degraded-host hits, max per-backup load, distinct backups used — by calling the real select_backups directly (no RPC needed). It shows degraded-host avoidance is weight-independent while load-balancing is driven by the capacity term's -20 decay, so the default weighting is a principled choice. See the Reproduce page (step 6) and paper §V-G.

decay_sensitivity.py

Are the load-decay constants (−20, ×0.95) ad hoc?

Sweeps the decay mechanics themselves — the capacity decrement over {5,10,20,40,80} and the health-decay factor over {0.80…1.00} — with the scoring weights fixed, across all four topologies × 5 seeds, by monkey-patching backup_selector's constants. Shows degraded-host avoidance is decay-independent while load-balancing responds smoothly and monotonically, so the published (20, 0.95) is a characterized, conservative choice. See the Reproduce page (step 6) and paper §V-G.

baseline_comparison.py

Would a decentralized hash placement (CRUSH/Dynamo-style) suffice?

Adds decentralized baselines from backup_selector.py — plain hrw, weighted rendezvous hashing (weighted_hrw), Dynamo-style weighted consistent hashing (weighted_chash), and a fairer random-offset round-robin (rr_random) — and compares them structurally against the feature-aware methods across the star scales and multi-hub topologies. Shows the weighted hash schemes avoid degraded hosts but load-balance more loosely than the lightly-coordinated heuristic, that rr_random exposes round-robin's real degraded-host risk, and that the findings hold on multi-hub graphs. See the Reproduce page (step 7) and paper §V-H, Table IX.

rl_algorithm_comparison.py

Is the RL load-balancing gap a PPO quirk, or the problem itself?

Runs the trained PPO and DQN policies side by side across all four scales and scores them structurally — distinct backups used, peak per-backup load, degraded-host assignments. Those are properties of the mapping rather than of RPC timing, so they are hardware-independent and reproduce exactly on any machine, unlike latency. Shows both algorithms concentrating the same way as the action space grows, with DQN collapsing to 1–3 backups of 80 at 128 hosts. Needs no RPC servers. See the Reproduce page (step 8) and paper §V-F, Table VII.

exp_package/ & config.py

DEFT's own code, the thing being tested

exp_package/Two_phase_commit/ holds DEFT's real Primary and Backup 2PC classes. We run them unchanged, including the default SimpleXMLRPCServer settings, whose limit of 5 waiting connections turns into a real finding at 128 hosts. config.py holds DEFT's network constants, plus a one-line import fix.

rl_model*.zip

Trained PPO and DQN models, one per network size

PPO: rl_model.zip (9 hosts) · rl_model_scaled.zip (16) · rl_model_scaled32.zip (32) · rl_model_scaled128_v3.zip (128, the fixed model described on the 128-host page) · rl_model_scaled128_collapsed.zip (128, the collapsed first attempt, kept so you can see it for yourself).

DQN (used for the cross-algorithm check, step 7 of the Reproduce page): rl_model_dqn.zip (9) · rl_model_dqn_scaled.zip (16) · rl_model_dqn_scaled32.zip (32, the collapsed default config) · rl_model_dqn_scaled32_mitigated.zip (32, after widening exploration) · rl_model_dqn_scaled128.zip (128, which still collapses to 3 backups of 80).

An RL policy is tied to a fixed number of hosts, so each size needs its own model, for both algorithms.
